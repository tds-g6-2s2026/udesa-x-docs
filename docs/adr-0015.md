# ADR-0015. Agente único de backoffice con Bedrock, MCP y sanciones confirmadas

- **Estado:** Propuesta
- **Fecha:** 2026-11-02
- **Alcance:** backoffice, admin-service, auth-service, posts-service, API gateway y futuros backoffice-agent y udesa-mcp
- **Seguimiento:** [IA-01 / issue #63](https://github.com/tds-g6-2s2026/udesa-x-project/issues/63), parte de la [épica #62](https://github.com/tds-g6-2s2026/udesa-x-project/issues/62)

## Contexto

El backoffice necesita un asistente para consultar la disponibilidad actual de los servicios, revisar publicaciones y recomendar medidas de moderación. Cada ejecución debe comenzar por un pedido del administrador. Una sanción requiere confirmación humana explícita y verificable por el backend.

La propuesta funcional «Agente único de Backoffice», del 30 de octubre de 2026, plantea Amazon Bedrock como LLM principal y Jev de TypeSafe como evaluador de decisiones estructuradas. Jev se integra como una herramienta del agente.

La plataforma existente condiciona la solución:

- Admin está escrito en Go, tiene PostgreSQL propio, sesiones administrativas, roles `superadmin` y `moderator`, buscador de usuarios, bloqueo/desbloqueo, auditoría y monitor de servicios.
- El código del frontend vive en `admin-service/internal/web`. El pipeline también lo construye como sitio estático y lo publica en S3 con CloudFront. La API administrativa se consume bajo `/api/admin/`.
- La sesión usa cookie HttpOnly y un header anti-CSRF. La identidad administrativa es independiente de la sesión de usuarios móviles.
- El gateway tiene un timeout de upstream de 10 segundos y construye la respuesta completa en memoria. No implementa streaming de respuestas.
- Posts expone un contador para el backoffice; falta una lectura administrativa paginada de publicaciones. La auditoría disponible tampoco reemplaza una API específica de antecedentes por usuario.
- Auth expone bloqueo/desbloqueo. La advertencia y la suspensión temporal necesitan contratos y comportamiento propios.
- La cuota versionada del namespace `tds-group-6` es de 8 pods. Los seis servicios existentes y los dos nuevos sumarían ocho; falta verificar ocupación y capacidad reales.

Estos datos provienen del código versionado revisado para IA-01, no de una inspección del despliegue vivo. Este ADR registra una propuesta de implementación; su publicación no acredita que las integraciones estén desplegadas.

## Decisión

### Componentes y recorrido

Conservar admin-service en Go y agregar dos servicios Python:

| Componente | Responsabilidad |
|---|---|
| Frontend existente del backoffice | Chat, evidencia, progreso y modal de confirmación. |
| admin-service | Autenticación y autorización, conversaciones, ejecuciones, propuestas, confirmaciones y auditoría. |
| backoffice-agent | LLM principal en Bedrock, cliente MCP y ciclo acotado de herramientas. |
| udesa-mcp | Servidor MCP sobre HTTP interno, herramientas con contratos tipados y adaptadores hacia APIs existentes y Jev. |
| auth-service | Estado de acceso de usuarios, bloqueo, revocación y futura suspensión temporal. |
| posts-service | Fuente de verdad del contenido de publicaciones. |

```text
Navegador (frontend existente, publicado en S3/CloudFront)
  -> /api/admin/... -> API gateway -> admin-service
                                      -> backoffice-agent -> Amazon Bedrock
                                             -> udesa-mcp -> APIs internas
                                                         -> TypeSafe Jev (HTTPS)
```

El agente y MCP se despliegan como Deployments con Services ClusterIP, sin Ingress público. El backend administrativo continúa como entrada autorizada para el navegador. Se agregan sus configuraciones y pipelines siguiendo los repositorios existentes.

### Propiedad de datos

Admin guarda conversaciones, mensajes, estado de ejecuciones, evidencia consultada, evaluaciones, propuestas y auditoría mediante migraciones Goose. Agente y MCP utilizan APIs de admin y no se conectan a su PostgreSQL. Las publicaciones se leen por API de posts y el acceso de una cuenta se modifica por API de auth.

Las copias de evidencia son acotadas y tienen identificador, usuario, instante, cobertura y relación con una ejecución. Permiten explicar qué se evaluó aunque después cambie el contenido de origen. Su retención y el tratamiento de contenido protegido o eliminado deben acordarse antes de habilitar moderación con datos reales.

### Identidad, permisos y herramientas

El catálogo contiene seis herramientas:

| Tool | Efecto |
|---|---|
| `get_services_health` | Lectura de disponibilidad actual. |
| `get_user_posts` | Lectura de publicaciones y registro de evidencia consultada. |
| `get_user_history` | Lectura de antecedentes y registro de su cobertura. |
| `evaluate_with_jev` | Evaluación externa de evidencia con política versionada. |
| `propose_sanction` | Creación de una propuesta pendiente, sin sancionar. |
| `execute_sanction` | Aplicación de una propuesta aprobada por un administrador autorizado. |

Los esquemas de entrada, salida y errores se describen en [Contratos del asistente de backoffice](contratos-ia-backoffice.md).

Admin obtiene identidad y rol de su sesión vigente. Entre servicios se autentica al llamador y se valida una delegación limitada a administrador, conversación, ejecución, operaciones permitidas y vencimiento. El mecanismo criptográfico y la rotación de credenciales se especificarán antes de implementar los endpoints internos; no se considera suficiente confiar únicamente en la red del cluster.

La cookie del navegador, las claves de proveedores y las autorizaciones de confirmación quedan fuera del contexto del modelo. Los argumentos de una tool no pueden elegir administrador, rol o credenciales. El UUID del usuario se resuelve con el buscador existente; una búsqueda ambigua exige que el administrador seleccione la cuenta antes de iniciar la revisión.

Las cinco primeras tools pueden participar del ciclo del LLM según sus permisos. `execute_sanction` queda reservada al flujo de confirmación controlado por backend: no se habilita como una acción libre del modelo. Un mensaje de chat como «confirmo» no emite autorización.

### Ejecución del chat

El frontend envía un mensaje autenticado a admin. Admin valida sesión y CSRF, persiste la ejecución y devuelve `202 Accepted` con `run_id`, antes del límite del gateway. El frontend consulta el progreso por ese identificador.

Estados de ejecución: `pending`, `running`, `completed`, `failed` e `interrupted`. El despacho y el callback hacia el agente usan autenticación interna, límites de concurrencia y correlación por `run_id`. Una conversación solo es accesible por el administrador autorizado según la política de acceso que se acuerde.

Cada ejecución tiene límites configurados de pasos, tokens, duración y contexto. La consulta periódica de progreso no inicia inferencia ni renueva indefinidamente una sesión sin actividad humana. Los errores de proveedor se muestran como tales, sin inventar datos.

Un reinicio o pérdida del proceso debe dejar un resultado fallido o interrumpido consultable, detectado por un deadline persistido. No se recuperan automáticamente acciones sensibles ni se deja una ejecución en espera sin límite. Un nuevo pedido humano puede iniciar otra ejecución.

### Disponibilidad bajo demanda

`get_services_health` reutiliza el sondeo del monitor de admin mediante una API interna que toma una muestra nueva. Consulta los seis `/health` en paralelo, con destinos configurados y timeout por servicio. El resultado incluye estado, código HTTP cuando exista, latencia e instante de observación.

La API actual del panel devuelve observaciones en caché y no incluye código HTTP: necesita una adaptación para cumplir este contrato. Una falta de respuesta se informa como no disponible desde ese punto de observación, sin atribuir una causa ni inferir el estado de bases o dependencias.

El monitor periódico y sus alertas de la historia #55 continúan separados del agente. Sus eventos no disparan inferencia.

### Moderación y confirmación

1. Resolver usuario y obtener publicaciones y antecedentes mediante APIs autorizadas.
2. Guardar evidencia acotada y enviar a Jev solo el contexto necesario y una política versionada.
3. Validar respuesta tipada, referencias y restricciones determinísticas. Baja confianza, falta de evidencia o error externo deriva a revisión humana.
4. Registrar una propuesta inmutable con UUID de usuario, tipo de sanción, duración, motivo, evidencia, política, autor y vencimiento.
5. Mostrar en el modal los datos canónicos de esa propuesta, obtenidos del backend.
6. Al confirmar, admin vuelve a comprobar identidad, rol actual, pertenencia, versión y expiración. Genera una autorización para esa operación exacta.
7. El flujo confiable invoca `execute_sanction`; admin aplica las reglas de dominio y llama a auth cuando corresponde. Se guarda el resultado real y se audita con el administrador confirmante.

Cambiar usuario, acción, duración o motivo requiere una propuesta nueva y otra confirmación. Cancelar o dejar expirar una propuesta no modifica la cuenta.

La autorización se asocia a una sola operación de negocio. La operación tiene una clave idempotente estable también en el servicio que aplica el efecto. Doble clic, concurrencia o reenvío no aplican dos sanciones. Ante timeout después de enviar una acción se consulta el resultado por operación antes de reintentar; una respuesta desconocida no se presenta como éxito ni como rechazo definitivo.

Propuesta y confirmación se pueden registrar transaccionalmente en admin, pero no hay una transacción compartida entre las bases de admin y auth. Se persisten intención, identificador de operación y resultado con estados explícitos para reconciliar un desenlace incierto sin repetir el efecto.

El bloqueo existente se reutiliza. La futura suspensión temporal se valida en auth, invalida sesiones y deja de restringir al vencer sin depender del agente. El vencimiento no revive sesiones revocadas ni levanta un bloqueo permanente. La advertencia requiere definir previamente su efecto y canal de entrega.

### Proveedores y operación

Bedrock se consume mediante SDK y una identidad de pod con permisos mínimos para el modelo o perfil elegido. El rol usado por GitHub Actions para desplegar no acredita permisos de inferencia del pod. Se valida Pod Identity o IRSA según el soporte y permisos reales del cluster.

La clave de Jev se inyecta como Secret. Se verifica conectividad HTTPS y se limita el contexto externo. Los posts y respuestas externas se tratan como datos no confiables: no cambian instrucciones, permisos, políticas o destinos de red. Los timeouts y reintentos de evaluaciones son acotados.

Se registran `run_id`, tool, versión de modelo/política, latencia y uso de tokens disponible, sin claves ni cookies. Se implementa un feature flag y un procedimiento de rollback. La habilitación de sanciones requiere completar la validación de autorización, idempotencia y auditoría.

## Alternativas

- **Integrar todo en admin-service:** reduce pods, pero acopla el servicio Go al SDK del LLM, al cliente MCP y al ciclo del agente. Se eligen servicios Python separados para aislar esas integraciones. La capacidad real de EKS es una condición para mantener esta elección.
- **Llamar al modelo desde el navegador:** expondría credenciales y desplazaría la autorización fuera del backend. Se conserva la mediación de admin.
- **Usar solo Bedrock para evaluar moderación:** simplifica proveedores. Se elige Jev como evaluador tipado conforme a la propuesta funcional, sujeto a comprobar contrato, acceso y calidad con contenido del proyecto.
- **Chat síncrono o streaming en el MVP:** exige ajustar el recorrido completo de timeouts o streaming. Se elige ejecución identificada con respuesta rápida y consulta de estado.
- **Moderación por eventos, métricas nuevas o base vectorial:** agregan infraestructura y procesamiento fuera del alcance del chat bajo demanda.

## Consecuencias

A favor:

- Se reutilizan sesión, permisos, buscador, bloqueo, auditoría y sondeo existentes.
- Las reglas y escrituras quedan en los servicios dueños de los datos.
- La evidencia, la propuesta y la confirmación permiten explicar y auditar decisiones sensibles.
- Las respuestas largas de IA no obligan a aumentar el timeout general del gateway.

En contra:

- Se agregan dos servicios y una dependencia de dos proveedores externos.
- Los ocho pods previstos ocupan toda la cuota versionada; falta margen y capacidad efectiva por verificar.
- La persistencia de trabajos y los fallos entre servicios requieren estados e idempotencia explícitos.
- La revisión administrativa y las copias de evidencia necesitan una política acordada de acceso y retención.
- La calidad de moderación depende de evaluación en español y de una política versionada; la confianza del modelo no sustituye la decisión humana.

## Validaciones pendientes y condición de aceptación

| Pendiente de IA-01 | Evidencia requerida |
|---|---|
| Cuenta, región, modelo o perfil de Bedrock | Invocación mínima controlada y registro del identificador y permisos efectivos. |
| Cuenta, clave y contrato real de Jev | Evaluación con contenido ficticio y respuesta tipada válida; límites y versión registrados. |
| Capacidad y conectividad EKS | Cuotas y uso actuales, recursos asignables, número de pods y salida a proveedores. |
| Identidad entre servicios | Contrato verificable de identidad/delegación, audiences, permisos, vencimiento y rotación; autorización de ejecución fuera del LLM. |
| Política y RBAC | Roles de lectura/propuesta/confirmación, categorías, umbrales, duraciones, canal de advertencia y reglas de evidencia insuficiente. |
| Privacidad y retención | Acceso a posts protegidos/eliminados, datos enviados a terceros, cobertura de historial y plazos de conservación. |
| Contratos y recuperación | Revisión de los esquemas adjuntos, deadlines y consulta/reconciliación de operaciones inciertas. |

En la terminal de trabajo revisada para esta propuesta no hay credenciales AWS utilizables, contexto de kubectl seleccionado ni `TYPESAFE_API_KEY` en el entorno del proceso. Esto no demuestra que falten en otros entornos; las pruebas reales siguen pendientes.

El ADR pasa de Propuesta a Aceptada después de la revisión del equipo y del registro de estas validaciones en IA-01. La PR documental no cierra por sí sola el issue #63. Las implementaciones se distribuyen en [IA-02 a IA-13](https://github.com/tds-g6-2s2026/udesa-x-project/issues/62).

## Fuera de alcance

Prometheus/Grafana, métricas históricas nuevas, GPU, base vectorial, moderación proactiva, procesamiento de denuncias por cola, apelaciones automáticas, análisis de logs y acciones de infraestructura como reiniciar o escalar pods.
