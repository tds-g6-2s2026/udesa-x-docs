# ADR-0003. PostgreSQL como fuente de verdad y Redis para datos que vencen

- **Estado:** Aceptada
- **Fecha:** 2026-08-13
- **Alcance:** auth, posts y social

## Contexto

El enunciado pide al menos dos tipos de base de datos. Además, varios datos tienen una vida corta y conocida: el link de verificación de email dura 24 horas, el de recuperación de contraseña dura 10 minutos, y hay contadores por hora, bloqueos por intentos fallidos y tokens revocados.

## Decisión

PostgreSQL guarda todo lo permanente. Redis guarda lo efímero, siempre con tiempo de vida (TTL) y con un prefijo por servicio: `verify:`, `reset:`, `auth:login-attempts:`, `auth:account-lock:user:`, `auth:revoked-token:`, `posts:rate:` y `social:follows:rate:`. Los contadores usan operaciones atómicas de Redis. En producción se usa un Redis gestionado, fuera del cluster.

## Alternativas

- Guardar todo en PostgreSQL, con una columna de vencimiento y un proceso periódico de limpieza.

## Consecuencias

A favor:

- El vencimiento es automático y no hace falta un proceso de limpieza.
- Los contadores siguen siendo correctos aunque lleguen pedidos simultáneos.

En contra:

- Si Redis pierde sus datos, se pierden los links pendientes y los contadores. Se acepta porque el usuario puede volver a pedirlos.
- Hay un componente más para configurar y operar en cada entorno.
