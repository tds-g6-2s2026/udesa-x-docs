# ADR-0002. Una base de datos por servicio, sin claves foráneas entre servicios

- **Estado:** Aceptada
- **Fecha:** 2026-08-19
- **Alcance:** auth, posts, social, media y admin

## Contexto

Si dos servicios comparten tablas, un cambio de esquema en uno puede romper al otro, y se pierde la posibilidad de desplegarlos por separado.

## Decisión

Cada servicio tiene su propia base PostgreSQL y es el único que la lee y la escribe. Las referencias a datos de otro servicio se guardan como UUID sin clave foránea. Por ejemplo, `posts.author_id` y `follows.follower_id` guardan el id de un usuario de auth. Para leer datos de otro servicio se usa su API ([ADR-0010](adr-0010.md)). Cada servicio versiona su esquema con sus propias migraciones: Alembic en Python y goose en Go.

## Alternativas

- Una base compartida, con un esquema por servicio.
- Claves foráneas entre tablas de distintos servicios.

## Consecuencias

A favor:

- Los esquemas evolucionan de forma independiente.
- La falla de una base no tumba a los demás servicios.

En contra:

- La base no garantiza integridad referencial entre servicios. Si un usuario se da de baja, sus follows quedan en social hasta que exista el evento correspondiente ([ADR-0010](adr-0010.md)).
- Las consultas que cruzan datos de varios servicios se resuelven en código, con pedidos en lote.
