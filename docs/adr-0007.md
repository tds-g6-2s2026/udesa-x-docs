# ADR-0007. API gateway propio con verificación central del token

- **Estado:** Aceptada
- **Fecha:** 2026-09-14
- **Alcance:** api-gateway y auth

## Contexto

La app no debería conocer la dirección de cada servicio. Además, la revocación de tokens ([ADR-0006](adr-0006.md)) solo la conoce auth.

## Decisión

Un api-gateway escrito en FastAPI recibe todo bajo `/api` y rutea según la primera palabra de la ruta:

| Primera palabra | Servicio |
|---|---|
| `auth` | auth-service |
| `posts` | posts-service |
| `follows`, `follow-requests`, `users` | social-service |
| `media`, `files` | media-service |
| `admin` | admin-service |
| cualquier otra | responde 404 |

Para todo lo que no es auth ni admin, el gateway verifica el token con `GET /auth/introspect`, guarda la respuesta 30 segundos en memoria y reenvía el pedido con las cabeceras `X-User-Id` y `X-User-Handle`. auth y admin pasan sin verificar porque manejan su propia autenticación.

## Alternativas

- Un gateway administrado, como AWS API Gateway.
- Usar el Ingress del cluster como único punto de entrada, sin gateway propio.

## Consecuencias

A favor:

- La app usa una sola URL.
- La revocación de tokens se respeta en todos los servicios.
- La caché evita una llamada a auth en cada pedido.

En contra:

- Un token revocado puede seguir pasando hasta 30 segundos.
- La caché vive en la memoria de un proceso. Con varias réplicas, cada una tendría la suya.
- Mientras tenga una sola réplica, el gateway es un punto único de falla.
